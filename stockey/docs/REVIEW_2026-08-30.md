## 1. Confirmed: IST/UTC bug silently truncated every live intraday sync (HIGH, fixed)

**What was found.** `data/dhanlive/ohlcv.py`'s `choose_intraday_refresh_end`/
`choose_daily_refresh_end` fell back to bare `datetime.now()` whenever no
explicit `to_date` was supplied (the normal case for the daily incremental
sync and for the tail end of any backfill run). This host's system clock is
UTC. Every naive datetime elsewhere in this module is treated as IST wall-clock
(`MARKET_CLOSE_HOUR/MINUTE = 15:30`, `with_market_close()` does a bare
`.replace()` with no timezone conversion) — a convention that silently breaks
the moment "now" is computed on a UTC-clocked host instead of supplied
pre-converted by a caller.

**Verified against real data, not just reasoned from code.** Bulk historical
data (2023–2025) is correct: 375 bars/day, 09:15–15:29 IST exactly. But every
day from 2026-08-14 onward — i.e. since the daily incremental sync started
running — is short:

```
affected ticker-days (bars < 370) since 2026-08-14: 4,211
bar counts observed: as few as 89 of the expected 375 bars/day
```

A representative case (RELIANCE): every day Aug 17–26 stopped at exactly
`09:44:00 UTC` = `15:14 IST`, 16 minutes before the real 15:30 IST close — a
naive-UTC "now" reading Dhan's API accepted at face value instead of rejecting
or converting.

**Fix.** Added `data/dhanlive/ohlcv.py::_ist_now()` — the one correct
definition of "now" for this module (UTC system clock + 5:30) — and replaced
every live "now" fallback with it (`choose_intraday_refresh_end`,
`choose_daily_refresh_end`, `sync_intraday_ohlcv`'s first-sync `from_date`
default, and `scripts/backfill_intraday_5yr.py`'s own `target_start`/`now`,
which had the identical exposure for its own most-recent days). 5 new tests
(`data/dhanlive/ohlcv.py`'s block in `tests/test_data_platform.py`) — this
exact `to_date=None` path had **zero** test coverage before this review, which
is how it shipped and ran for two weeks unnoticed.

**What this does NOT fix.** The code fix stops *new* gaps; it does not repair
the 4,211 ticker-days already stored short. See `docs/DATA_COVERAGE.md`'s
"Still open" section for the exact query to find them and the repair this
still needs (a targeted re-fetch, not a full re-backfill).

## 2. Confirmed: `deal_flow.py`'s fixed lookback window permanently drops old deals (HIGH, fixed)

`fundamentals/screens/deal_flow.py` filtered `nseindia_block_deals`/
`nseindia_bulk_deals` by a fixed trailing `CURRENT_DATE - 10 days` window, with
no persisted state. `data/nseindia/offmarket.py` (the same day's todo #1) can
by its own design fall behind by more than 10 days (`MAX_CONSECUTIVE_FAILURES`
explicitly anticipates multi-day NSE blocks) and its very first run after
revival lands up to 365 days of history in one shot — none of which
`deal_flow.py` would ever have turned into an alert, silently and permanently,
since nothing re-scans older dates.

**Fix.** `load_last_processed_date()` reads the max `disclosure_date` already
recorded for `source='deal_flow'` and `load_recent_deals()` scans forward from
there (with a 2-day overlap buffer) instead of a fixed window from today — a
stall of any length self-heals on the next run that finds new deals, rather
than being permanently truncated. First-ever run (no watermark) uses a wide
365-day window matching `offmarket.py`'s own default. Verified live against
the real DB (temporary rows created and removed) that both branches — first
run and watermark-based — produce correct results.

Also fixed as part of the same change: the date comparison now casts
`date::date` explicitly, matching the defensive convention every other NSE
date comparison in this codebase already uses (found by the datetime audit;
low severity on its own, bundled into this fix since it's the same query).

## 3. Confirmed: a false pledge-fetch failure could manufacture a false alert storm (HIGH, fixed)

`fundamentals/screens/l2_state.py::fetch_pledge_levels` already defaults an
absent company to `pledge_pct=0.0` ("unpledged, the overwhelmingly common
case") — fine for a static snapshot field. But a *total* fetch failure (the
existing `except Exception: pledge_levels = {}` path) is indistinguishable
from that same default, and the new pledge-trend logic (`compute_pledge_trend`,
today's todo #2) diffs the *current* run's value against the *prior* stored
value. A failed run would store a false `0.0` for the whole universe; the next
successful run would then see any real pledge value as "increasing" —
manufacturing a `pledge_increase` alert (and, via `watchlist_exit.py`'s
widened `INVALIDATING_TRIGGER_TYPES`, potentially a false thesis invalidation)
for every previously-pledged company simultaneously.

**Fix.** `build_l2_state_row()` takes a `pledge_data_available` flag; on a
total fetch failure the trend fields are written as `None` (no trend
claimable) while `pledge_pct` itself keeps its pre-existing 0.0-default
behavior, unchanged in scope.

## 6. Confirmed: `technicals.py`'s watchlist-coverage fix had two residual gaps (MEDIUM, fixed)

- `run_technicals_refresh()` returned immediately when the L1 universe
  snapshot was empty — *before* `load_watchlist_only_tickers()` was ever
  called, silently defeating the exact 2026-08-22 fix that added it (a
  watchlist company outside L1 must still get refreshed). Fixed: falls
  through with an empty L1 frame instead of returning early; the natural
  empty-DataFrame path through the rest of the function (verified —
  `upsert_to_db` already no-ops on an empty frame) produces the same
  all-zeros result when *both* sources are genuinely empty.
- `load_watchlist_only_tickers()` queries `fundamentals_watchlist.status`, a
  column bootstrapped by `watchlist_exit.py` from within `notifications.py` —
  which runs *after* `technicals` in `run_pipeline.py`'s `STEPS`. A truly
  fresh DB's first-ever pipeline run could hit this before the table/column
  exist. Low real-world impact (self-heals from the second run onward) but
  fixed with the same defensive try/except-and-degrade treatment every other
  market-wide query in this pipeline already gets.

- `fundamentals_events.disclosure_date`/`announcement_timestamp` are still
  plain `TEXT` columns (pre-existing, not introduced by this work) — every
  current writer follows the bare-`date()` convention correctly, but there's
  no DB-level type enforcement stopping a future writer from silently
  breaking the exact-text-match dedup this relies on. Worth a real migration
  if this table gains more writers; out of scope here.
- `all_dhan_intraday_sync.sh` (13:25 UTC) runs only 5 minutes after
  `all_price_adjustment.sh` (13:20 UTC) with a comment implying the gap

  provably racy (separate lock files, disjoint tables) but the stated
  rationale isn't guaranteed either. Left as-is; worth widening if it's ever
  actually observed to race.
